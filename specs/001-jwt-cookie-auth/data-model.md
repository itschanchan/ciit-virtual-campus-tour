# Data Model: JWT Cookie Access

**Feature**: JWT Cookie Access (001-jwt-cookie-auth)
**Date**: 2026-11-04

## Entities

### User

Represents a registered person who can authenticate and access protected campus tour administration features.

| Field | Type | Required | Unique | Validation Rules |
|-------|------|----------|--------|------------------|
| `_id` | ObjectId | Yes | Yes | Auto-generated by MongoDB |
| `email` | String | Yes | Yes | Must be a valid email format; lowercase before storage |
| `passwordHash` | String | Yes | No | Must be a bcrypt/argon2 hash (never plaintext); min 60 chars |
| `createdAt` | Date | Yes | No | Auto-generated on record creation |

**Identity rule**: Email is the unique login identifier (clarified: email address only). Email uniqueness is enforced at the database level via a unique index.

**Lifecycle/state transitions**: A User record is created during registration (out of scope for this feature — assumes existing user data). A User is "authenticated" when a valid JWT is issued; no persistent session row is stored (JWT is stateless; state lives in the client cookie).

### Session (derived, not stored)

A Session is a derived concept representing an active authenticated period tied to a User. It is not a separate database collection.

| Attribute | Source | Lifetime |
|-----------|--------|----------|
| `userId` | JWT subject (`sub` claim) | While JWT is valid |
| `expiresAt` | JWT expiration (`exp` claim) | `JWT_EXPIRES_IN` (24h) |
| `cookieAttributes` | Server configuration | While cookie exists in browser |

**State transitions**: Session begins on successful login (JWT issued, cookie set). Session ends on JWT expiration, logout (cookie cleared), or cookie deletion/blocking by the browser.

## Validation Rules from Requirements

- **FR-001**: Email must be provided and match an existing User record; password must be provided and verified against `passwordHash`.
- **FR-002**: On successful auth, a JWT is signed with the User's `_id` as the subject and stored in a cookie.
- **FR-003**: On subsequent requests, the JWT is read from the cookie and verified; if valid and unexpired, the request is treated as authenticated.
- **FR-004**: Logout clears the authentication cookie.
- **FR-005**: Requests to protected endpoints without a valid cookie JWT are rejected.
- **FR-006**: Requests with an expired JWT are rejected and require re-authentication.

## Relationships

- A User has zero or more derived Sessions (concurrent logins from multiple devices are allowed; each produces a separate JWT/cookie pair).
- No foreign-key relationships to other entities in this feature.
